# 共享知识库（审核 + 自动批准代理）

一句话：**群聊采集包由「知识审批代理」判断——唠嗑直接拒绝、他人经验保留（可剥离无关行）；AI 提议/联网查证过的回复/手动添加走审读，命中违禁词的永远转人工**。
只有 approved 的条目才会被检索、才会进入提示词。

## 为什么要有审核

聊天和联网检索里学到的东西，有相当一部分是错的、过时的，或者只是某个人随口一说。
不审核直接进提示词，等于把噪音固化进人格里，而且事后没法撤回。所以这里的设计是：

```
聊天 / 联网检索 ──► 提议（pending） ──► 控制台审核 ──► 批准（approved）──► 检索池 ──► 提示词
                                    └─► 驳回（rejected，可恢复）
```

## 数据长什么样

`bridge/state/knowledge.json`，一条记录：

| 字段 | 说明 |
| --- | --- |
| `text` | 一句自洽的陈述句，脱离上下文也能看懂（例：`群 1019799335 的管理员是 大肥鱼`） |
| `tags` | 可选标签，最多 8 个（`人物` / `偏好` / `群规` …） |
| `source` | `chat`（聊天里学到的）/ `web`（联网检索查证的）/ `manual`（你手动加的） |
| `group` | 来源会话 key（`group:123` / `private:456`），审核时可改 |
| `private` | `true` = 只在来源会话可见；`false` = 全群共享（默认） |
| `status` | `pending` / `approved` / `rejected` |
| `embedding` | 向量（base64 Float32），只在 `approved` 且 embedding 可用时存在 |
| `hits` / `lastHitAt` | 被检索命中的次数，用来判断一条知识是否真的有用 |

去重按「去掉空白标点后的小写文本」算指纹：同一句话重复提议只会返回既有条目，不会堆两份。

## 两个入口

### 1. AI 主动（二代仿真）

- `qq_knowledge_search(key, token, q, k)` — 只读检索已批准条目，返回 `score` 与 `mode`（`vector` / `keyword`）
- `qq_knowledge_propose(key, token, text, tags, source, private, note)` — 提议一条，**只进待审队列**

预设 `qq-chat-v2` 里已经写了使用规则（【知识库】/【知识库卫生】两节）：先查再提议、只记事实、
敏感信息标 `private`、不重复提交。两个工具都受「二代仿真 → 工具开关」控制（`knowledgeSearch` / `knowledgePropose`）。

### 2. 控制台「知识库」页

- **待审**：逐条批准 / 编辑 / 驳回，也可以勾选多条批量批准、批量合并（合并会保留最早那条，其余标记 `rejected` 并备注去向）
- **已批准**：按内容/标签过滤；可改「仅本群 / 共享」；「试检索」输入一句话就能看到实际命中与相似度
- **已拒绝**：可恢复并批准，或彻底删除
- 手动添加时如果勾了「仅来源群可见」，**必须填来源会话 key**（`group:1019799335` 这种）；不填会被接口直接拒绝 —— 没有来源的私有条目谁都看不见，属于死数据
- 手动添加同样先进待审——人工整理的东西也值得多看一眼再入库

## 审批代理（knowledge.autoApprove.mode = agent）

| 项 | 行为 |
|---|---|
| 包体编号 | 采集包每条消息带 `[n]` 编号，结构化存进条目的 `lines`，代理能按行剥离 |
| 代理判断 | 独立 DSH 会话（与群聊同一安全 preset/模型），读带编号的包，逐包裁决 |
| 工具 | `qq_knowledge_approver_pending`（看积压）/ `_pack`（重读单包）/ `_verdict`（keep/reject，可带 `keepLines`、`text`、`tags`、`reason`）。令牌由桥接按 worker 会话临时发放，普通群聊会话拿不到。**工具由 DSH 启动时加载**：新加/改过 MCP 工具后需要重启 DSH 才会出现在会话工具列表里；未刷新时审批代理会退回「严格 JSON 裁决」（`[{id,verdict,keepLines,reason}]`），入库语义一致 |
| 违禁词闸门 | 放行前再扫一遍改写后的文本；命中就拦截（`autoBlocked` 只留人工） |
| 并行与扩容 | `maxWorkers` 默认 4、`batchSize` 12；**积压 ≥ `backlogThreshold`（默认 50）时立刻拉满并行**；worker 完成即复查，还有积压就继续补位（带 1s 防抖 + 失败指数退避） |
| 回退 | `mode: 'rules'` → 旧规则代理（违禁词 + 专业词 + 联网核实）；`collect.direct: true` → 采集包不审读直接入库 |

## 采集直采（knowledge.collect.direct）

| 项 | 行为 |
|---|---|
| 采集包 | 每分钟每个会话打包一次（最多 20 条他人文字），正文是 `群聊片段时间：人：话；…` |
| 直采入库 | `store.ingest()` 直接写 `approved` + 计算 embedding，`directIngested: true`，下一次检索即可命中 |
| 不经过代理 | 不再等自动批准代理攒批，也不经过人格读与会话；采集与检索完全解耦 |
| 违禁词闸门仍在 | `add()` 里照常扫描：命中就只打 `autoBlocked`、保持 `pending`、不做向量，交给人工/代理 |
| 库满 | 优先淘汰**最旧直采条目**给新包腾位；人工添加的、AI 提议的不动 |
| 联网查证过的 AI 回复 | 仍走 `pending` + 人工放行（`exempt` 凭据不能直采） |
| 回退 | `knowledge.collect.direct: false` → 退回全量待审 + 自动批准代理 |

## embedding 后端

在「知识库 → 设置 → 向量检索」里三选一，改完点底部的「测试向量连接」：

| 后端 | 配置 | 说明 |
| --- | --- | --- |
| 关闭 | — | 只用关键词检索（中文二元组 + 英文分词），零依赖、零延迟 |
| 本地 Ollama | `http://127.0.0.1:11434/v1` + `nomic-embed-text` | 先 `ollama pull nomic-embed-text`；全离线、不要 key |
| 云端 | 任意 OpenAI 兼容 `/v1/embeddings` + key | 硅基流动 `BAAI/bge-m3`、阿里百炼 `text-embedding-v3`、OpenAI `text-embedding-3-small` 都行 |

**两种情况会自动重建**：在设置里改 `backend`，或改 `local.model` / `cloud.model`，保存后桥接会立刻在
后台重跑一遍已批准条目（控制台会提示「正在后台重建向量」）。同一次请求不会等它跑完。

**手动按钮「重建全部向量」是同步的**：每批 16 条，单次最多处理 500 条，某批失败就当场停下
（返回 `done` / `failed` / `remaining`），控制台等它返回；条目超过 500 时会提示「还有 N 条没处理，
再点一次继续」。云端按条计费，500 条约等于 500 次 embedding 调用。

不需要重建的情况：只换 key、只调 topK/阈值/字数这些参数（向量不变）。

不重建会怎样：检索会比对条目里记录的 `embeddingModel`，**与当前模型不一致的条目一律不参与向量排序**
（维度相同也不行——不同模型的同维向量互不可比），自动退回关键词参与，因此不会出现分数错乱的排序。
但它们的语义检索能力等于暂时失效，所以换完模型还是应该点重建。

**降级行为**：embedding 请求超时（默认 1.5 s）或失败时，这一轮直接用关键词检索，日志记一行；
不会因为 embedding 服务挂了就不回消息。

## 自动批准代理

审核全人工的代价是：AI 提议十条，你得点十次，多数还没问题。代理把这件事变成
「攒够一批自动放行，有风险的挑出来给你看」。

```
聊天消息（他人文字）──► 采集器（每分钟一包，每包≤20条）──┐
AI 提议 / 控制台手工添加 ───────────────────────────────┤
                                                      ▼
                                                   pending
                         ┌────────────┬───────────────┼────────────────┐
                         ▼            ▼               ▼                ▼
                    命中违禁词   库内已有同义内容   无专业词      命中专业词
                         │            │               │                │
                         │            │               │        联网核实（官方/百科？）
                         ▼            ▼               ▼           ┌────┴────┐
                    打标拦截      直接批准        直接批准      有→批准   无→打标拦截
```

**触发条件**：**待处理**（未拦截、未豁免）条目数 ≥ `batchSize`（默认 20）就跑一轮。入库、AI 提议之后会顺手检查一次，
另有定时巡检（默认 60 秒看一眼）。不满 20 条时**一条都不动**。上一轮因 `maxVerifyPerRun` / `maxRunMs`
没用完而被延后的条目算「已知未完成工作」，下一轮接着做，不受阈值卡。

**已拦截的不会再送审**：打上 `autoBlocked` 的条目从此不进候选，跑多少轮都不会再联网核实、
不会再送判定模型，也不会再花 token——它只是留在待审队列等你逐条确认。所以被拦的攒到几百条也
**不会**变成「无限自动审」；代价是它们会一直占着待审队列，所以控制台表头把
「待处理 / 已拦截 / 联网豁免」分开报数，并给了「只看待处理」的过滤。人工改正文或标签会清掉标记，
那一条才重新进入流程。

**超期归档**：被拦截后 `archiveDays`（默认 30）天无人处理的条目，由巡检顺手挪到「已拒绝」，
备注追加「超期未确认：拦截于 X，N 天无人处理」。只动**被拦截**的——正常待审还在等自动批准排队，
不按时间清。归档保留 `autoBlocked` / `verification` 全部凭据，`archivedAt` / `archivedFrom`
记下来源，控制台「已拒绝」页显示「⏳ 超期未确认」并给「放回待审」按钮（`POST /api/knowledge/restore`）。
`archiveDays=0` 关闭归档。这样待审队列不会被几百条拦截条目越堆越长，也不会把它们挤出
`?limit=500` 的窗口。

**违禁词闸门**：内置 240 条、12 类（赌博博彩 / 毒品药物 / 武器爆炸 / 色情低俗 / 未成年人 /
暴力自伤 / 诈骗黑产 / 隐私侵犯 / 违禁交易 / 涉政涉恐 / 技术滥用 / 其他风险）。
匹配前会归一化（小写、去标点空格、全角转半角、去零宽字符），所以「赌 博」「Ｖ Ｐ Ｎ」这类简单绕过无效。
正文和标签都会被扫。

- 命中即打 `autoBlocked` 标记，**状态仍是 pending**，只等你人工确认；代理再跑多少次都不会放行它。
- 人工改写正文或标签后标记自动清除、重新过闸（改干净了下一轮会被放行，还带违禁词就继续拦）。
- 控制台「批准选中」会**跳过**被拦截条目并提示，只有单条「确认批准」能放行——闸门不能靠批量操作绕过。
- 想加词：控制台设置页最下面的文本框，每行一个，随保存生效。

**可审计**：放行的条目带 `autoApproved: { at, by: 'auto-approve-agent' }`，拦截的带
`autoBlocked: { at, reason, hits: [{ term, category }] }`，都能在 `/api/knowledge` 的回包里看到。

**风险面（请正视）**：打开代理就等于「AI 自己写的东西会直接进知识库、再注入人格会话」，只是被违禁词挡了一层。
误判、过时信息、群体偏见照样可能进来。建议：把 `batchSize` 调大（比如 50）降低频率，
定期翻一眼已批准列表，或者直接 `enabled: false` 退回全人工。

## 聊天采集

群聊是知识的主要来源，但不能把整段对话原样灌进来。采集器的取舍：

| 收 | 不收 |
| --- | --- |
| 别人的文字消息 | **自己（AI）的发言**——否则模型会把自己的幻觉当成群友事实收进来 |
| 同一分钟内的多条 | 图片 / 表情 / 语音 / 转发（没有可核实的事实文本） |
| 保留发言人 + 原话 | `/` 开头的命令、纯标点、短于 `minChars` 的碎句、同人连续重复 |

**打包规则**：每个会话每分钟最多打一包，一包最多 20 条（满 20 条立即打包，不等窗口结束）。
不足 `minMessages`（默认 **1**）条的这一分钟直接丢弃。默认放到 1 是因为实测：群聊多是「一两句就停」，
阈值卡 3 条会让整包被丢掉，`115988912` 曾连续 8 包全丢、群友的话一条都没进库。
噪声改由 `minChars`（6 字）和每小时包数上限压住，碎片交给自动批准/人工筛。
嫌吵就把 `minMessages` 调回 2~3，代价是稀疏对话基本收不到。
每会话每小时最多 `maxPacksPerHour` 包（默认 200），超出丢弃，避免刷屏群把库灌满。

打包产物长这样（`source: chat`，`tags: ['聊天汇总']`）：

```
群聊片段（10-25 12:03，3 人 5 条）：甲：今晚八点群里有活动，记得来。；乙：好的，我会准时到场的。……
```

**它不归纳、不改写、不删减**：采集器只负责「把碎片合并成一条待审记录」，要不要变成结论由审核环节判断。

### 配置

```json
"collect": { "enabled": true, "windowMs": 60000, "maxMessages": 20, "minMessages": 1, "minChars": 6, "maxPacksPerHour": 200 }
```

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 关掉即完全不采集 |
| `windowMs` | `60000` | 打包窗口（毫秒），最小 5000 |
| `maxMessages` | `20` | 每包最多几条，满了立即打包 |
| `minMessages` | `1` | 少于几条就整包丢弃（调到 2~3 只收密集讨论） |
| `minChars` | `6` | 单条短于几个字丢弃 |
| `maxPacksPerHour` | `60` | 每会话每小时打包上限 |

## 人格联网回复的豁免

「绝不收自己（AI）的发言」这条有个例外：**这一轮它真的查过网**。

判据是工具调用，不是模型自称——桥接在 DSH 事件流里看到 `mcp__web-search-safe__web_search`
（记下 `query`），并且这一轮成功发出过消息，才把这几条回复当成「有据可查的候选事实」。
新的一轮开始（`turn/start`）就清空上一轮的凭据，所以「上一轮查过」豁免不了这一轮。

| 情况 | 处理 |
| --- | --- |
| 没查过网就自己说了一句 | 照旧丢弃（`skipped: 'no-search'`） |
| 查过网、且这一轮发出来了 | 入库，`tags: ['联网回复']`、`proposedBy: 'web-reply'`、带 `exempt` 凭据，进**待审** |
| 查过网但命中违禁词 | 入库照旧打 `autoBlocked` 标记，仍要人工看 |
| 查过网的条目 | **不进自动批准**：`exempt` 的判据是「查过」，不是「核实过」，一律留给人 |

条目不打包、不进群聊缓冲：AI 的回复本身就是一条独立陈述，混进「群聊片段」既读不懂也审不了。

`exempt` 长这样（`publicItem` 对外可见，控制台待审行显示「✅ 联网豁免：这轮查过 …」）：

```json
"exempt": { "kind": "web-search", "queries": ["原神 米哈游", "原神 开放世界"], "at": 1792914618137 }
```

自动批准代理遇到豁免条目只报数量（`exempt`），不去碰它们；一批全是豁免条目时直接跳过。

## 联网核实

只对「命中专业词」的内容核实。词库内置 **1041 条、16 类**（时政新闻 / 编程开发 / 游戏 /
科技互联网 / 医疗健康 / 法律 / 金融经济 / 历史 / 地理 / 物理化学 / 生物 / 体育 / 影视音乐 /
军事 / 教育考试 / 交通出行）。命中只是「值得查一下」，不代表内容错。

核实顺序（先便宜后贵）：

1. **先查知识库**：已批准条目里有同义内容（关键词覆盖 ≥ `kbDupScore`，或归一化后完全相同）
   → 直接放行，`verifiedBy: knowledge-base`，不联网。
2. **再联网**：取命中的最长 2 个专业词去搜（走桥接已有的 `web-search`：DeepSeek 联网优先，Bing 兜底）。
3. **看来源分级**：
   - `official`：`*.gov.cn`、官媒（新华社/人民网/央视等）、国际组织、或标题含「官方网站/官方文档」的厂商站 → 放行
   - `wiki`：维基百科、Fandom、灰机 wiki、萌娘百科、百度百科 → 放行
   - `weak`：只有论坛/UGC 之类的非权威结果 → **拦**
   - `unknown`：搜不到，或搜索本身不可用（没配 key、断网）→ **拦**
   - `contradicted`：结果里出现「辟谣 / 谣言 / 不实」信号 → **拦**（优先级高于 official）

**它挡不住什么（必须知道）**：只判断「有没有可靠来源」，**不判断来源内容是否支持这句话**。
搜到「原神」的百科页，不代表「3.2 版本上线了纳西妲」这句是真的。真正的一致性校验还得靠人。
反过来说，因为 Bing 几乎总能返回点什么，实际上「因为没有来源被拦」的情形不多，
拦截主要发生在**搜索不可用**和**辟谣信号**上——本机没配 DeepSeek 搜索凭据时会退到 Bing，
两者都失败时所有命中专业词的条目都会被拦下来转人工，这是刻意的安全默认。

**性能**：每轮最多核实 `maxVerifyPerRun` 条（默认 10），单轮总预算 `maxRunMs`（默认 90 秒），
超出的条目留到下一轮（返回 `deferred`）。同一词 30 分钟内复用结果，不重复打接口。

### 搜索后端（Tavily / DeepSeek / Bing）

核实的第一步是「搜得到」，这一层可切换后端：

| provider | 需要凭据 | 说明 |
| --- | --- | --- |
| `tavily` | **不需要**（keyless） | 官方搜索 API，中英文都准；keyless 有速率限制，填了 API Key 走正式额度并解锁 `advanced` 深度 |
| `deepseek` | 需要 `DEEPSEEK_API_KEY` | 本机目前没有，所以默认不会选到 |
| `bing` | 不需要 | 抓 Bing 页面，最不稳定（会返回无关站，甚至被反爬挡住） |
| `auto`（默认） | — | 依次试 **Tavily → DeepSeek → Bing**，前一个失败才回退下一个，并在 `note` 里写清为什么回退 |

Tavily 走 `POST https://api.tavily.com/search`：

```
有 key  → Authorization: Bearer <key>
无 key  → X-Tavily-Access-Mode: keyless      # 免 key，限流
```

返回的 `content` 映射成统一的 `snippet`（判定模型的输入）；`score` 低于 `minScore`（默认 0.2）的结果会被丢掉——
keyless 偶尔会混进完全不相干的页面，低分过滤 + 后面的「查询词相关性过滤」两道一起挡。

控制台「联网搜索后端」可以切 provider、填 key、选深度、调最低分/结果数，还有一个**试搜一次**按钮
（`POST /api/knowledge/search-test`，只读，不改配置）。

两个实测出来的关键机制：

1. **整句优先检索**：语义引擎搜整句远好于搜孤立名词。搜「Docker」只能得到名词解释，搜
   「Docker 容器默认走 bridge 网络」能直接命中官方文档里那句话。所以陈述长度 4–120 字时，
   先拿整句搜一次（标记 `kind: claim`），再逐词补搜；整句太短就纯逐词。
2. **结果轮转合并**：每个查询词各取一条再取第二条…… 否则 `maxSources` 会被第一个词占满。
   早先「原神 是 开放世界 游戏」先搜「开放世界」，判定模型只看到解释开放世界概念的文章，
   得不出「来源提到原神」，把真话判成 unclear。

相关性判据是「标题/摘要里出现**任一**专业词」——整句检索时不会因为页面没写整句原文就被丢掉。

### 判定模型（来源支不支持这句话）

来源分级只回答「这个网站可不可信」，回答不了「它支不支持这句话」——搜到「原神」的百科页，
不代表「3.2 版本上线了纳西妲」是真的。判定模型补的就是这一层：

```
有官方/百科来源 → 判定模型（陈述 + 来源标题/摘要）→ supported 才放行
                    ├─ contradicted：来源与陈述矛盾 / 辟谣 → 拦
                    ├─ unclear：来源没提到关键信息 → 拦
                    └─ 模型不可用 → 规则兜底（见下）→ 仍不放行
```

**主路径**走 DSH 的独立会话（和「自我介绍」同一套范式）：单独建 workspace + 安全 preset，
提示词里要求只回 JSON `{verdict, confidence, reason}`。它不在任何群里说话，事件只被收集，
不会被当成 QQ 回复发出去；也没有 bash/文件读写权限（判定提示里塞着群聊原文，绝不能落到默认 preset）。

**规则兜底**（模型失败、超时、回不出 JSON 时启用）只做一件事：
**陈述里的数字/版本/日期，来源里必须有**。编造的事实十有八九死在数字上：

| 陈述 | 来源摘要 | 判定 |
| --- | --- | --- |
| 原神 3.2 版本上线了纳西妲 | …最新版本 4.1… | `unclear`（3.2 找不到） |
| 原神 3.2 版本上线了纳西妲 | …3.2 版本新增角色纳西妲… | `supported` |
| 某地 12 月 5 日发生地震 | 官方辟谣：网传地震消息不实 | `contradicted` |

另外会检查强断言（全部/唯一/最/必然）在来源里有没有对应表述，以及引号里的实体名有没有出现。
规则判定置信度上限只有 0.55，且**永远不放行 unclear**。

判定标准是**分级**的，不是「必须逐字对上」：

1. 来源讲的是不是同一个主体？讲别的主题 → `unclear`
2. 陈述里的硬事实（数字/版本/日期/比例/金额/专有人名机构名）来源里出现过吗？完全没有 → `unclear`
3. 与陈述矛盾（含辟谣）？ → `contradicted`
4. 同一主体、无矛盾、能指出来源里支持该陈述的具体表述 → `supported`；**措辞不同不算矛盾**
   （来源写「动作角色扮演」，陈述写「开放世界」，不构成 unclear）
5. 来源只是泛泛介绍主体、完全没涉及陈述断言的那件事 → `unclear`

实测效果（真实联网 + 真模型）：`原神是米哈游开发的开放世界游戏` → supported 放行；
`原神 7.9 版本上线了能秒杀所有 boss 的角色` → unclear 拦截（来源无 7.9 版本信息）；
`Docker 容器默认走 bridge 网络` → supported 放行（官方文档原句）。

判定结论落库在 `verification.judgement`（`verdict / reason / source: model|rules|rules(degraded)`），
事后能回答「当时凭什么判它不可信」。

### 核实配置

```json
"verify": {
  "enabled": true, "kbDupScore": 0.75, "maxVerifyPerRun": 10, "maxRunMs": 90000,
  "judge": { "enabled": true, "timeoutMs": 25000, "maxSources": 3 }
},
"webSearch": {
  "provider": "auto",
  "tavily": { "enabled": true, "apiKey": "", "keyless": true,
              "searchDepth": "basic", "minScore": 0.2, "maxResults": 6, "timeoutMs": 20000 }
}
```

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 关掉则「命中专业词也直接放行」（只留违禁词闸门） |
| `kbDupScore` | `0.75` | 库内复用阈值：越高越严格，0.75 相当于查询词四分之三都在库里出现过 |
| `maxVerifyPerRun` | `10` | 每轮最多联网核实几条 |
| `maxRunMs` | `90000` | 单轮总时间预算 |
| `judge.enabled` | `true` | 关掉则「有官方/百科来源就放行」，不做语义判定 |
| `judge.timeoutMs` | `25000` | 单次判定超时，超时即降级到规则 |
| `judge.maxSources` | `3` | 送进判定的来源条数（越多越准，也越费 token） |

## 注入与检索

- 每条消息投递前，取该会话最近 4 条消息拼成查询（`knowledge.queryWindow`），检索 `topK`（默认 5）
- 命中条目拼成【知识库参考】块插在提示词末尾（`injectMaxChars` 默认 1200 字），并提示模型「与本轮无关就忽略」
- 同一会话、同一查询 5 分钟内复用上次结果（`cacheTtlMs`），避免每条消息都打一次 embedding
- `private: true` 的条目只在 `group` 与当前会话 key 相同时才会被检索到

**来源群**：采集按会话分群打包（每个群独立缓冲、独立成包），条目上带 `group` 字段。
检索接口和 MCP `qq_knowledge_search` 的命中结果都**带 `group`**，能看出这条来自哪个群。
自动注入人格会话的提示词时还会额外标注 `［来自 group:xxx］`——**只在跨群时标**，避免把别的群的
情况当成当前群的事实。

## 配置项（`config.json` → `knowledge`）

```json
{
  "enabled": true,
  "backend": "off",
  "local": { "baseUrl": "http://127.0.0.1:11434/v1", "model": "nomic-embed-text" },
  "cloud": { "baseUrl": "", "apiKey": "", "model": "" },
  "topK": 5,
  "minScore": 0.25,
  "injectMaxChars": 1200,
  "maxEntries": 3000,
  "searchTimeoutMs": 1500,
  "allowPropose": true,
  "autoApprove": { "enabled": true, "batchSize": 20, "intervalMs": 60000, "extraTerms": [] }
}
```

- `minScore`：向量相似度下限，低于它的命中不算（关键词模式不用它）
- `maxEntries`：条目上限，到了就拒绝新增，避免状态文件无限变大
- `allowPropose: false`：关掉 AI 提议入口，只允许控制台手动添加

## 自测

```bash
npm run test:knowledge   # 20 项：存储/检索/向量/降级/超期归档
npm run test:guard       # 13 项：违禁词表 + 自动批准代理
npm run test:collect     # 27 项：聊天采集 + 专业词 + 联网核实 + 判定模型 + 联网豁免（不联网，假搜索/假判定注入）
npm run test:autoapprove # 7 项：积压不重送、阈值只数待处理、延后条目续跑（不联网）
```

**积压 7 条**（`test:autoapprove`）：40 条已拦截零新增连跑 5 轮 verify 0 次、新条目只核实一次、
40 条积压 + 1 条新增（阈值 20）不触发、积压 40 + 干净 20 只放行干净那批、延后条目下一轮续跑、
违禁词先拦不核实、结果带 `candidates` 计数。

**存储与检索 20 条**（`test:knowledge`），不联网：假 fetch 顶替 embedding 端点（OpenAI 与 Ollama 两种返回形状各测一遍），
覆盖去重、pending 不进池、批准后可检索、private 可见性、向量排序、embedding 挂掉退回关键词、
换模型未重建时旧向量被忽略（且重建后恢复）、reindex 如实上报 remaining、合并、落盘重载、
提示词块截断、容量上限、探测失败原因、公开展示不带向量、超期归档只动拦截项且幂等、
归档条目放回待审后拦截标记仍在。

**代理与闸门 13 条**（`test:guard`）：词表 ≥200 且无重复/单字、空格全角零宽绕过、五条正常群聊不误伤、
标签藏词、入库即标记、不满 20 条不动手、满批放行 20 且入库即拦、拦截条目幂等、改写触发重扫、
关闭即停工、自定义词生效、`autoApproved` 审计字段、已批准条目不得事后打标记。

另有服务端回归 `R19`（真起 HTTP）：阈值触发、违禁转人工、再跑不动、关闭即停；
`R22`：联网豁免全链路——无凭据丢弃、有凭据进待审、API 返回凭据、自动批准不接管；
`R23`：超期归档——`archiveDays` 透出、`restore` 只接受归档条目（非归档条目拒绝）。

**采集与核实 27 条**（`test:collect`）：专业词 1041/16 类 + 英文词边界不误伤；采集器丢弃自己/命令/媒体/短句、
不足 1 条整包丢弃（默认放开到 1，见上）、满 20 条立即打包、每会话每小时封顶；来源分级（gov/官媒/维基百科/标题含「官方」兜底）；
核实五种判定（official/wiki 放行，weak/unknown/contradicted 拦截）；搜索抛错必须判 unknown；辟谣信号优先；
同词缓存只打一次接口；代理三条处置路径（无专业词直批、wiki 放行、杂站拦截并留 `verification`）；
关闭核实后不联网但仍拦违禁词；每轮核实上限与 `deferred`；库内已有同义内容免核实直接批准并记 `duplicateOf`。
判定模型：JSON 回复解析容错（代码块/夹带/裸写法）；规则兜底抓硬事实（版本对不上→unclear、对得上→supported、
辟谣→contradicted）；模型异常降级为规则且**不放行**；核实+判定「官方来源但内容不支持」→ unclear 拦截；
判定为矛盾 → contradicted 拦截；代理端到端把 judgement 落进 `verification`；搜索结果与查询词无关时判 unknown（不是 weak、更不是放行）；Tavily 响应映射（去重/丢低分/content→snippet）、
keyless 与 Bearer 两种身份、429 限流与 401 凭据提示、provider 配置解析；
联网豁免三条：没有搜索凭据的 AI 回复照旧丢弃、查过网的回复单独入库并携带查询凭据、
自动批准代理跳过豁免条目只报数量。
